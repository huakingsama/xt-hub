# 架构与设计取舍

## 1. 为什么是"一个文件 + 纯标准库"

部署目标是**别人手里的机器人**，不是自己的开发机。用户可能只有 SSH，没有 pip 源，
系统还是 Python 3.6/3.7 的老发行版。所以：

- **单文件**：`scp` 一个 `hub_server.py` 就完事，回滚就是换回旧文件。
- **零依赖**：HTTP 服务、会话签名、PNG 手写编码全部用标准库实现，不依赖 Flask/Pillow。
- **单进程**：没有数据库、没有消息队列，状态在内存 + 一个 JSONL 审计文件里。

## 2. 三种"连接"的角色

| 角色 | 权限 | 典型用户 |
|---|---|---|
| admin | 管理用户、看审计、也能遥控 | 实验室负责人 |
| operator | 接管后遥控 / 建图 / 存图 | 同学、队友 |
| viewer | 只能看画面 | 讲师、评委、参观者 |

权限设计的原则：**看不需要成本，开需要负责**。所以读接口一律 `登录即可`，
写接口一律 `持租约 token`。

## 3. 租约（lease）而不是锁

文件锁的问题：进程崩了锁不释放，谁都拿不到车，只能人工去删文件。

所以用时间租约：

```
claim  → 服务端发 token，记录 (holder, expire = now + 90s)
心跳   → 每 30s 续约一次
超时   → 自动释放，下一个人可以直接接管
```

代价是"人还在但网断了"会被抢走，这在教学场景里是可接受的——**丢控制权比丢整台车好**。

## 4. 画面为什么是代理而不是直连

机器人上已有三个画面服务（相机 8090、地图 8091、融合 8093）。hub 的作用不是重造，
而是**同源化**：

```
浏览器 ──► hub:8000/rgb.png ──► 机器人本机 :8090
```

好处：
- 浏览器只需要记住一个地址、一次登录；
- 画面服务的端口不用暴露给每个人；
- hub 可以统一加缓存、限速、日志。

代价是多一跳转发，局域网里可以忽略（实测 1080p MJPEG 延迟增加 < 20ms）。

## 5. 演示模式（--demo）为什么重要

没有机器人时，整条链路（登录 → 接管 → 看画面 → 遥控 → 录制 → 回放）都应该能演示。
所以 demo 不是"假数据占位"，而是**用同一套渲染管线生成合法画面**：

- 地图：真做射线投射（房间四面墙 + 门洞），累积成一户型图；
- 融合：雷达扇形 + 深度点云楔形，走同样的色彩映射；
- 位姿：与地图使用**同一组运动方程**，否则叠加会错位（踩过这个坑）。

这让"讲方案"和"写代码"可以并行：UI 在 demo 上改，硬件好了直接切真机。

## 6. 已知限制

| 限制 | 原因 | 影响 |
|---|---|---|
| 只支持局域网 | 无 TLS、默认密码 | 不要暴露公网 |
| 遥控依赖 `/cmd_vel` 订阅者 | 底盘驱动/里程计未起时为 0 | 车不动，但页面不报错 |
| 导航目标点依赖 `move_base` | 本车未部署导航栈 | 点地图会明确提示"无订阅者" |
| 位姿来自建图算法而非里程计 | 无轮式编码器 | 打滑时位姿会漂 |

## 7. 关键实现细节（踩过的坑）

1. **`HTTPServer` 是单线程的** → 页面请求会排在图片请求后面，浏览器表现为**白屏**。
   必须用 `ThreadingHTTPServer`，并对重渲染的图做 450ms 缓存。
2. **`302` 必须带 `Location`**，否则浏览器渲染 0 字节响应体 = 纯白。现改用
   `200 + meta refresh + location.replace + 手点链接` 三保险，iframe 里也不会白。
3. **`SO_REUSEADDR`** 允许同端口起多个进程，调试时"改了代码没生效"多半是旧实例在应答。
4. **`do_GET` 忘了 `parse_qs`** 会让带参数的接口静默返回空。
5. 桥接进程（`teleop_bridge.py`）必须是 **python2 + rospy**（ROS kinetic 的限制），
   hub 是 python3，两者用 HTTP 通信，不要试图 import。
